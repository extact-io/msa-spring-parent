■ ExceptionTranslationFilterによるAuthenticationExceptionのハンドル
・多くの認証フィルタ（例：BearerTokenAuthenticationFilter, BasicAuthenticationFilter）は、自分で AuthenticationException を捕まえ
  その場で AuthenticationEntryPoint を呼ぶ。そのため、Flter外にAuthenticationExceptionがthrow されることは通常ない
・なので、認証ファイルの後段にいるExceptionTranslationFilterで通常AuthenticationExceptionをハンドルすることはない
・ExceptionTranslationFilterでAuthenticationExceptionをハンドルするケースは後段のAuthorizationFilterで認可しようとしたときに認証情報
  が取得できないエッジケースに限定される。なので、AuthenticationExceptionをハンドルすることがない訳ではないが、かなりそのケースは
  かなりレアとなる

■ Filterで誰にもハンドルされない例外
・最終的にはTomcat(アプリケーションサーバー)まで例外が戻され、web.xmlのerror-page属性に従い、エラーページにforwardされる
・web.xmlのerror-page属性が定義されていない場合は、デフォルトで/errorページにforwardされ、該当ページないのでクライアントに変えるエラーが404になる
・なので、RESTの場合はきちんと自分でハンドルして明示的にエラーレスポンスを返すことが必要

■ ServiceConnectionを使った複数接続先
・@ServiceConnectionを使って(JdbcConnectionDetailsなど)同じ種類の接続先を複数同時に使うことはできない
・ServiceConnectionを使った接続先設定はAutoConfigurationで解決されるが、AutoConfigurationは簡易設定のため、
  ServiceConnection以外も含め同じものが複数ある場合の使い分けは考慮されていない
・AutoConfigurationは@ConditionalOnBeanや@ConditionalOnMissingBeanなどのある型のBeanがあるかないかで条件を
  絞っていて、存在する場合は利用者側でJavaConfigにより手動で設定することが基本となる
・ServiceConnectionもこれと同じように接続先を表すConnectionDetailsの型が同じインスタンスが複数ある場合、
  どっちを使うか決定できなくなる。
・よって、ServiceConnectionもAutoConfigurationと同じように複数の接続先を同時に扱うことはできない

■ @PathVariableのパラメーター名を省略するかしないか
@PathVariable Long ownerId とするか @PathVariable("ownerId") Long ownerIdとするか？
結論は省略する。理由は以下のとおり
・Springの公式リファレンスも省略で統一されている
・Terasolunaでも以前は明示することを推奨していが、その記載が削除されている（つまり、やっぱり省略でもいい気がしてきたという考えがあると思われる）
・一番心配なのはリファクタリング時だが必ずテスト対象にはなるハズなのでその点は問題ないと考える

    ### 明示的な書き方
    - **メリット**
      - URLテンプレートとバインド先の対応が明示されている
      - 引数名をリファクタしてもバインディングは壊れない
      - ツールでの補完や読みやすさが向上
    - **デメリット**
      - 少し冗長
    ### 暗黙的な書き方
    - **メリット**
      - スッキリ書ける
      - 小さなコントローラーでは十分読みやすい
    - **デメリット**
      - **引数名とパス変数名が一致していないとバインディングに失敗**
      - **リファクタリング時にミスしやすい**（引数名だけ変わるとバインドエラー）



■ BeanValidation
・ネストプロパティのConstraintsのアノテーションは静的に到達可能な定義にする
・BeanValidationはフィールドではなくgetterの定義を優先するため、Constraintsが取得できなく、結果バリデーションが掛からなくなる場合がある
・例えば次のクラスに対する"id.id"プロパティに対するバリデーション実行が指定された場合、Identityにgetterがあるため、Constraintsが
  testModel.id.Identity#getId()で辿られ、Identity#getId()にはConstrainsがないためチェックなしとなる。
・BeanValidationはgetterにConstrainsがなければ対応するフィールドの定義を見ていってくれるが、Identityはインタフェースなのでそれもなしとなる。
    ⇒ なぜかEclipseの実装ではConstrainsが見つからないが、まったく同じコードをF11のデバックで実行するとConstraitsが見つかって期待通りに動く
       場合があるが、基本的にクラスのメタ情報のキャッシュかなにかの副作用で不安になるので「静的に到達可能な定義にする」が大原則となる
    static class TestModel {
        private Identity id; // getterはなし
    ...
    static record TestModelId(
            @RmsId
            int id) implements Identity {
    ...
    public interface Identity {
        int id();
        default int getId() {
            return this.id();
        }
    ...
・「静的に到達可能な定義にする」ために気を付けるべきこと
    - getterが優先されるので、getterにフィールド定義とは異なる型を付けている場合は注意する
    - getterにConstraintsがない場合、プロパティ名と同名のフィールドのConstraintsが確認される。
      よって、getter名と異なるフィールド名にConstraintsを付けている場合は注意する

・Validationかけるのはgetterがなくてハマる可能性があるのでrecordではなく@Valueにした方が無難な気がする

## ユーザアカウントとユーザプロファイルの関係
- ユーザプロファイルはユーザアカウントを使っている人がどんな人なのかを補足する情報いなります
- ユーザアカウントが作成されるときは必ずユーザプロファイルの情報も登録されます
- ユーザアカウントを削除するとユーザプロファイルの情報も削除されます
- 作成済みのユーザプロファイルの情報を登録時とは別のユーザアカウントに付け替えることはありません
- ユーザアカウントの情報とユーザプロファイルの情報は同一トランザクションでまとめて更新される場合もありますが、それぞれ個別に更新される場合もあります

■ Viewインタフェースの導出
・interface層からDomainクラスへの参照はモデル変換を不要とするため許容しているがDomainクラスの状態を変更する操作は制限したいため、このインタフェースを設けいている。
・よって、interface層からDomainクラス本体への参照は禁止とする。
    ⇒ 補足：Port and Adapterは外部からはportに配置した要素への依存しか許容しない。よって、外部にモデルを公開する際は必ずモデル変換が必要となる。
             今回はアーキテクチャ決定はオニオンアーキテクチャが前提のため許容されるが、厳格なPort and Adapterアーキテクチャでは許容されないことは理解しておく必要
             がある。

■ interface層からの依存を許容するDomain要素
・Domain層にはアプリケーションの状態を変更する操作が含まれるためinterface層の依存は必要最低限にすることが好ましい。
・これを踏まえReferenceModelと値オブジェクト、ValidationのConstraintの3つはinterface層からの参照は許容する
・これらはいずれも副作用がなく、参照することによるデメリットは層を飛ばした参照の統制的な観点しかなく、参照させないことの合理性に欠けるため。

■ RequestとResponseとして外部に公開可能とする要素
・外部に公開して良いのはJava標準クラスおよびinterfaces層で定義したクラスのみ
・interfaces層から一部のDomainクラスに依存することは許容しているが、これを外部に直接公開するのはNG。
・外部との入出力にDomainクラスを利用した場合、外部からのリクエストやレスポンその変更影響を直接ドメインで受けることになるため、絶対に禁止

■ RequestとResponseのデータ構造の共通化は行わない
・例えば、aminとmemberには構造が全く同じItemのResponseクラスが存在するように外部インタフェースを司るレイヤでは機能間で同じまたはほぼ同じとなるデータ構造
  クラスが複数存在することがあるが、これに対しては共通化か行わず、あえて重複さておく。
・各機能は他の機能に関係なく、必要とするデータが変わる可能性は多分にある。各機能で利用するRequestとResponseを共通化してしまった場合、他の機能の入出力の
  変更が本来は全く関係ない他の機能に及ぶことになる。よって、機能間の重複はたままた現時点では同じだけと割り切り、共通化はしないこと。
・これはControllerクラスにも同じことが言える。Controller間で重複する手順を共通化したい場合、それを制限することはしないが、継承による共通化は行わず委譲で行うこと


■ ApplicationServiceからの入出力クラス
・入力はDomainモデルは使わず、Commandクラスを設け、モデル変換を行う。これはモデルの登録時の内容や更新範囲をコードで明確にする目的がある
・出力はDomainモデル(ReferenceModel)で返す。参照の場合、モデル変換を行っても同じモデルとなることが大多数となる。デメリットの更新系操作の公開は
  ReferenceModelを使うことで対処済みのため、実質的なデメリットはない。
・よってモデル変換を行わなくても可としている。（当然必要に応じてモデル変換を行うのは可で常にDomainモデルを返すことを制約するものではない

■ persistenceのサブパッケージ
・サブパッケージをfile,jpaといった方式で分けるか？それともitem, reservatioといったドメインで分けるかの選択があるが、永続化パッケージであることから主たる関心は
  方式となるため、方式で分けている
・fileやjpaなどの方式の下をさらにitem, reservationといった業務ごとに分ける選択肢もあるが、JPAのEntityScanはパッケージ単位でしか指定できない。
・業務ごとにパッケージを分けない場合、アプリケーション内のすべてのエンティティをScanするか/しないか？の単位でしか制御できなくなる。
・itemはjpaにするがreservationはfileにした場合でも不要なItemEntityがスキャンされることになる。
・これを防ぐため、方式の下は業務(集約)ごとにパッケージを切り、Scan対象を細かく制御できるようにする

★ハマりどころ
クラスに@ConfigurationProperties("app.datasource")をつけず@Beanで指定する場合、クラスを指定しない@EnableConfigurationPropertiesの指定が必要
    ⇒@EnableConfigurationPropertiesを指定することでオブジェクトに設定をバインドするConfigurationPropertiesBindingPostProcessorが有効になる
    ⇒なので、@EnableConfigurationPropertiesをつけないとConfigurationPropertiesBindingPostProcessorが登録されず、バインドが行われない
    →@EnableConfigurationPropertiesにConfigクラスを指定しない例はネットにないので、中々分からなかった

★ハマりどころ
@RequestParamにはrequired属性があり、クエリストリングがない場合はバリデーションを実行する前にMissingServletRequestParameterExceptionが送出される
よって、↓のように@RequestParamに@NotNullをつけても意味はない
    @RequestParam("from") LocalDateTime from,

@Validでオブジェクトに対してバリデートする場合、フィールドはprimitiveではなくラッパー型で定義する
    処理の流れは JSON→オブジェクトバインド→validateとなる
    よって、primitive型にした場合、意図しない初期値が代入される
    例）@NotNull @Min(0) int itemId
            とオブジェクトフィールドに定義した場合、そもそもnullはなくJSONデータが来なくても初期値で0になるためバリデートエラーとならない
            なので、
        @NotNull @Min(0) Integer itemId
            と定義すべき
    ただし、外部から必ずデータが代入されることが前提の場合は、primitive型でも問題ない
